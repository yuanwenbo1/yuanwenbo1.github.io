随着软件系统、移动应用和智能设备越来越复杂，测试工作正在从单纯的用例执行，逐步转向需求理解、环境准备、自动化执行、结果分析和经验沉淀的协同过程。

在这个过程中，人工智能可以帮助测试人员理解复杂信息、发现风险和组织测试思路，但它不应成为所有测试动作的唯一执行者。一个可靠的智能测试系统，需要同时具备理解能力、执行能力、工程约束和持续复用能力。

本文讨论一种面向智能测试助手的设计思路，重点关注整体架构、流程组织、职责边界和系统收益，不涉及具体产品实现。

## 一、设计目标

智能测试系统的目标可以概括为：

```text
设计有依据
执行可扩展
结果可验证
失败能闭环
资产可复用
协作有边界
```

具体来说，系统需要解决以下问题：

1. 测试结论必须有明确的需求、预期和证据依据。
2. 不同平台和不同设备的测试能力可以持续扩展。
3. 环境、账号、设备和数据不能因为信息缺失而被随意猜测。
4. 测试失败需要区分产品问题、环境问题、脚本问题和证据不足。
5. 历史测试用例可以逐步转化为可执行、可维护的自动化资产。
6. 多个测试人员可以独立贡献资产，并通过协作机制进行合并和审核。
7. 自动化执行应尽量减少不必要的模型调用，控制成本和延迟。

## 二、总体架构

系统采用“智能编排 + 专业能力 + 确定性执行”的分层架构。

```text
用户目标与测试资料
          ↓
      测试编排层
          ↓
  ┌───────┼────────┐
  ↓       ↓        ↓
需求理解  用例设计  结果分析
  ↓       ↓        ↓
       执行准备与能力绑定
                ↓
        本地执行运行时
                ↓
       证据、报告和经验
```

### 测试编排层

编排层是系统入口，负责识别用户目标和选择所需能力。它不替专业模块完成具体工作，也不强制所有请求经过完整测试生命周期。

例如：

- 用户只想生成用例时，只进入需求理解和用例设计。
- 用户提供已有用例并要求执行时，直接进入执行准备和执行能力。
- 用户只想分析结果时，读取执行证据并进入结果分析。
- 用户要求完整测试时，动态组合多个专业能力。

这种设计比固定流程更适合真实工作，因为测试任务的起点和目标并不总是相同的。

### 专业能力层

专业能力按职责拆分，包括知识上下文、需求分析、测试设计、执行、结果分析、报告和知识沉淀等能力。

每个能力拥有清晰的输入和输出，使用结构化产物进行交接。这样可以减少模块之间的隐式依赖，也避免一个智能体同时承担过多职责。

### 确定性执行层

执行层负责调用浏览器、移动设备、接口、数据库和测试框架等实际能力。它不根据自然语言临时猜测动作，而是执行经过校验的结构化测试操作。

## 三、为什么采用目标驱动流程

固定流程的优点是容易理解，但缺点是容易产生无效工作。一个已经完成绑定的历史用例，不需要每次重新分析需求；一个已经生成的报告，也不需要重新运行测试。

目标驱动流程把“用户想完成什么”作为第一判断条件：

```text
目标：生成用例
  → 需求理解
  → 测试设计

目标：执行用例
  → 用例读取
  → 执行准备
  → 本地执行
  → 报告

目标：完整测试
  → 需求理解
  → 测试设计
  → 执行准备
  → 本地执行
  → 结果分析
  → 报告结论
```

它带来的直接收益是：

- 减少不必要的步骤。
- 减少重复模型调用。
- 缩短执行路径。
- 允许从已有资料继续工作。
- 让不同类型的测试任务拥有相应的最小流程。

## 四、模型与确定性能力的边界

智能测试系统的关键设计原则是：模型负责理解，代码负责确定性，执行器负责操作。

### 适合模型的工作

- 识别需求范围和业务目标。
- 分析风险、歧义和缺失验收条件。
- 设计边界、异常、状态和组合场景。
- 根据历史问题提出测试关注点。
- 对失败现象进行语义层面的归因。
- 从测试结果中总结可复用经验。

### 应交给代码和执行器的工作

- 文件解析和格式转换。
- 规则校验和数据统计。
- 测试用例筛选。
- 环境信息加载。
- 浏览器、设备、接口和数据库操作。
- 断言判断和状态记录。
- 截图、日志和报告生成。

如果把确定性工作交给模型，系统会出现输出不稳定、结论难复现和成本不可控等问题。反过来，如果要求代码完成复杂的需求理解，也会降低系统对复杂业务的适应性。

因此，二者不是相互替代，而是相互配合。

## 五、测试用例的分层设计

测试用例应当区分业务语义和执行实现。

```text
业务语义
  ↓
执行绑定
  ↓
可执行资产
  ↓
实际运行结果
```

### 业务语义

描述测试要验证什么，包括：

- 测试目标。
- 前置条件。
- 业务步骤。
- 预期结果。
- 需求和知识来源。
- 测试数据要求。
- 清理意图。

### 执行绑定

描述如何在具体平台上完成测试，包括：

- 页面元素或控件定位。
- 接口地址和请求方式。
- 设备和应用信息。
- 数据库访问方式。
- 证据采集方式。
- 执行环境和资源要求。

### 可执行资产

可执行资产是经过绑定、校验和验证后，可以重复运行的测试定义。它不应与某一次运行结果混在一起，也不应因为一次失败就被自动修改。

这种分层可以避免业务预期随着页面定位器变化而被悄悄改变，也可以让同一个业务用例拥有不同的平台或机型执行变体。

## 六、执行前的完整性检查

测试系统最重要的安全原则之一是：信息不完整时不执行。

执行前应检查：

- 测试目标是否明确。
- 账号和权限是否具备。
- 设备是否连接并处于可用状态。
- 浏览器、设备工具和测试框架是否可用。
- 用例是否存在有效步骤和可判定预期。
- 测试数据是否准备完成。
- 执行策略是否允许当前动作。
- 是否存在清理和恢复方案。

只要存在阻塞信息，系统就应一次性列出缺失项，暂停执行，等待用户补充。系统不应根据经验自动填写设备、账号、地址、定位器或业务预期。

这样可以避免“看起来执行了，实际上执行目标不对”的虚假结果，也能让测试人员更快补齐环境。

## 七、可扩展的执行能力

执行能力采用统一的适配器模型。每种平台能力都遵循相同的生命周期：

```text
能力描述
  → 输入校验
  → 环境准备
  → 动作执行
  → 结果转换
  → 证据采集
  → 清理恢复
```

适配器可以覆盖：

- Web 浏览器。
- Android 和 adb/uiautomator2。
- iOS 或移动端自动化框架。
- HTTP、WebSocket、MQTT 和 gRPC。
- 数据库和数据一致性检查。
- pytest 等项目原生测试框架。
- 性能、可访问性、安全和视觉检查。

统一适配器模型的好处是，新增加一种执行能力时，不必重新设计整个工作流；只需补充能力描述、输入约束、执行实现和证据转换。

## 八、自动化资产与多人协作

自动化测试用例适合由 Git 管理，而不是由中央服务直接保存正文。

推荐的协作方式是：

```text
用户获取测试资产仓库
        ↓
创建个人或测试分支
        ↓
新增或修改自动化用例
        ↓
本地校验和执行
        ↓
提交变更
        ↓
Merge Request 审核
        ↓
合并主干
```

每个用户使用自己的分支，可以减少多人同时修改同一分支造成的冲突。插件只负责提交到用户明确指定的非主干分支，不自动批准或合并主干。

Git 适合保存：

- 自动化测试用例。
- 执行绑定。
- 测试脚本和公共函数。
- 测试数据模板。
- 机型和平台配置模板。
- 评审记录和变更历史。

截图、视频、日志和运行报告等大体积结果更适合保存在本地执行目录或独立对象存储。

## 九、中央服务的合理边界

中央服务的价值在于提供多用户可见性和统一索引，而不是替代本地执行。

中央服务可以保存：

- 项目和仓库配置。
- Git 分支和提交版本。
- 自动化资产索引。
- 测试运行状态。
- 产物引用和监控数据。
- 用户、机器和项目维度的统计。

中央服务不应负责：

- 实际执行浏览器、设备或接口操作。
- 生成和修改测试用例正文。
- 代替本地环境和资源管理。
- 根据状态推断测试是否通过。
- 自动完成需要人工确认的审核。

这种边界可以保留插件本地执行的灵活性，同时为团队提供统一的状态查看和资产索引。

## 十、失败分析与质量闭环

测试失败不等于产品缺陷。系统需要先对失败进行分类，再决定后续动作。

```text
执行失败
  → 失败信号
  → 证据检查
  → 失败分类
  → 缺陷候选或环境问题
  → 人工确认
  → 修复验证
  → 受影响用例回归
```

建议至少区分：

- 环境和网络问题。
- 账号、权限和数据问题。
- 定位器、等待和脚本问题。
- Adapter 或执行框架问题。
- 产品行为问题。
- 证据不足或状态未知。

只有当失败证据充分且排除了测试系统问题时，才应形成产品缺陷候选。缺少证据的结果应进入待补证据列表，而不是直接提报缺陷。

## 十一、报告与证据设计

测试报告应是执行事实的结构化表达，而不是模型对结果的重新想象。

报告至少需要回答：

- 执行了哪些用例。
- 哪些通过、失败、跳过或阻塞。
- 失败发生在哪一步。
- 预期和实际分别是什么。
- 使用了什么环境和执行能力。
- 是否采集了截图、日志或响应。
- 清理是否完成。
- 是否可以形成缺陷候选。

报告应同时服务于三类角色：

- 测试人员查看整体结果。
- 开发人员查看复现步骤和技术证据。
- 管理人员查看风险、覆盖和发布结论。

因此，报告既要有简洁摘要，也要保留可以追溯到原始执行记录的详细证据。

## 十二、效率与 Token 控制

智能测试系统的效率优化不能只依赖更快的模型，还需要减少不必要的模型调用。

主要原则包括：

1. 已有结构化用例直接执行。
2. 固定格式转换、校验、统计和报告由代码完成。
3. Skill 之间传递产物引用和版本，不复制全部正文。
4. 结果分析只读取失败、阻塞和未知部分。
5. 模型输出使用固定结构，减少无关解释。
6. 用例和执行计划按需生成，不提前生成全部缓存。
7. 相同输入和版本优先复用已有资产。

这样可以同时降低 Token 消耗、执行延迟和结果波动。

## 十三、设计收益

### 更可靠

执行事实来自适配器和断言，模型不会直接决定测试通过。

### 更灵活

用户可以只生成用例、只执行用例、只分析结果，或者组合完整测试。

### 更易扩展

通过统一适配器接入新的平台和测试能力，不需要复制整套流程。

### 更易复用

语义用例、绑定和执行资产可以在不同任务、环境和版本中复用。

### 更适合协作

Git 分支和评审机制管理测试资产变更，执行环境和运行结果彼此隔离。

### 更可控

执行前检查、权限约束、证据要求和清理机制共同降低误执行风险。

### 更节省成本

模型只参与真正需要理解的环节，确定性路径不消耗额外 Token。

## 结语

智能测试系统的核心不是把所有测试工作交给模型，而是重新划分智能和工程的边界：

```text
模型负责理解和推理
代码负责规则和统计
适配器负责实际操作
Git 负责资产协作
报告负责事实表达
人工负责关键确认
```

只有当这些职责边界清晰时，智能测试助手才可能从一次性的对话工具，逐步演进为可扩展、可复用、可审计的测试基础设施。
