很多团队开始使用 AI 辅助写测试用例后，都会遇到一个相似的问题：

AI 看起来很快。

给它一段需求，它马上能生成一批测试用例。

但真正拿去评审或执行时，问题也很明显：

- 需求理解可能不完整。
- 业务规则可能被猜测。
- 异常流程可能遗漏。
- 测试点和用例之间缺少追溯。
- 用例数量很多，但不知道哪些必须测。
- 有些预期结果看似合理，实际没有经过确认。

所以，测试用例设计 Skill 的关键，不是让 AI 更快地“写表格”，而是让 AI 按一套稳定的测试设计流程工作。

这篇文章总结一套经过脱敏整理的测试用例设计 Skill 工作流。它不绑定具体项目、业务系统、公司工具或内部资料，只保留可复用的方法。

## 一、为什么不能直接生成正式用例

测试用例不是从一句需求扩写出来的。

真正可靠的用例，前面应该有一条清晰的分析链路：

```text
需求条目 -> 功能点 -> 测试点 -> 测试维度 -> 风险来源 -> 测试用例
```

如果跳过前面的需求分析、功能抽取、测试点确认和风险回补，AI 生成的用例很容易变成“看起来完整，实际上不可控”。

更危险的是，AI 会把不确定信息写得很确定。

比如需求里没有说明异常处理口径，AI 可能直接写出“系统提示失败原因并允许重试”。这句话可能符合常识，但未必符合真实产品设计。

因此，测试用例设计 Skill 要遵守一个基本原则：

```text
先确认测什么，再确认怎么测、测多深，最后再生成正式用例。
```

## 二、整体工作流

测试用例设计 Skill 可以拆成十二个阶段。

```text
任务受理
  ↓
建立进度看板
  ↓
需求分析
  ↓
疑问整理与解答
  ↓
功能抽取
  ↓
测试点抽取
  ↓
门禁A：需求与测试点审核
  ↓
测试点分析
  ↓
测试维度映射
  ↓
风险与优先级分析
  ↓
用例生成预览
  ↓
门禁B：测试设计审核
  ↓
生成正式测试用例
  ↓
用例质量自检
  ↓
交付与评审
```

这套流程的重点不是增加形式，而是把 AI 的工作过程变得透明。

测试人员可以看到当前资料是否完整、哪些问题还没闭环、哪些测试点已经确认、哪些风险已经回补、哪些内容被裁剪，以及为什么裁剪。

## 三、第一步：建立当前进度看板

AI 辅助测试最容易失控的地方，是上下文状态不清楚。

用户陆续补充需求、原型、接口说明、技术口径、历史问题和测试环境信息后，如果没有状态管理，AI 很容易把旧信息和新信息混在一起。

所以，测试用例设计 Skill 应该先建立一个当前进度看板。

看板至少记录这些资料状态：

| 资料项 | 典型状态 | 作用 |
| --- | --- | --- |
| 需求说明 | 未提供 / 不完整 / 已确认 / 已冻结 | 判断目标、范围和业务规则 |
| UI 原型 | 未提供 / 不适用 / 待确认 | 影响页面交互和体验类用例 |
| 技术方案 | 未提供 / 不完整 / 已确认 | 影响状态机、异常恢复和数据一致性 |
| 接口文档 | 未提供 / 待确认 / 已确认 | 影响接口字段、错误码和状态码设计 |
| 历史缺陷 | 未提供 / 已确认 / 不适用 | 用于风险回补和回归用例 |
| 风险清单 | 未提供 / 已确认 / 不适用 | 用于高风险失效模式覆盖 |
| 测试环境 | 未提供 / 待确认 / 已确认 | 影响用例可执行性 |
| 发布范围 | 未提供 / 已确认 / 已冻结 | 影响覆盖深度和裁剪策略 |

状态建议统一为：

```text
未提供、已提供、不完整、待确认、已确认、已冻结、不适用
```

每次用户补充资料后，Skill 都应该先更新看板，再继续后续分析。

## 四、第二步：需求分析和疑问闭环

需求分析要解决的不是“写哪些用例”，而是先把需求讲清楚。

至少要回答这些问题：

| 分析项 | 要确认的问题 |
| --- | --- |
| 需求目标 | 这个需求解决什么问题 |
| 测试范围 | 本轮测哪些，不测哪些 |
| 用户角色 | 谁使用，谁受影响 |
| 主流程 | 正常业务路径怎么走 |
| 异常流程 | 失败、取消、超时、中断如何处理 |
| 业务规则 | 条件、阈值、状态、权限、限制是什么 |
| 输入输出 | 输入什么，系统产生什么结果 |
| 数据变化 | 数据如何创建、更新、同步或清理 |
| 外部依赖 | 依赖哪些接口、服务、设备、配置或账号 |

分析过程中发现的不确定项，要进入疑问清单。

疑问要区分阻塞和非阻塞：

| 类型 | 处理方式 |
| --- | --- |
| 阻塞缺口 | 不生成正式用例，先补齐或确认 |
| 非阻塞缺口 | 可以继续，但必须标注假设和影响 |
| 可选资料 | 建议补充，但不阻塞当前阶段 |
| 不适用项 | 明确本轮不涉及，不反复追问 |

比如需求目标、测试范围、关键业务规则不清，通常属于阻塞缺口。

历史缺陷、专项风险清单缺失，一般不阻塞基础用例设计，但会影响风险回补深度，需要在输出中说明。

## 五、第三步：功能抽取和测试点抽取

需求清楚后，不能马上写用例，还要先抽功能和测试点。

功能抽取的目标，是把需求拆成可测试对象。

可以按下面结构整理：

| 模块 | 功能 | 子功能 | 主流程 | 异常流程 | 依赖 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |

这里要注意两件事。

第一，不要把测试方法写成功能。

比如“验证按钮点击成功”不是功能，真正的功能可能是“用户提交配置”。

第二，不要把不可观察的实现细节当作测试对象。

测试对象应该能通过页面、接口、数据、日志、设备状态或其他证据进行验证。

功能抽取后，再抽测试点。

测试点关注“测什么”，不是完整操作步骤。

常见测试点类型包括：

- 正向：合法输入、正常流程、成功结果。
- 反向：非法输入、无权限、状态不满足。
- 边界：数值、时间、数量、长度、频率上下限。
- 状态：状态流转、重复操作、取消、恢复。
- 异常：超时、失败、断网、服务异常、数据异常。
- 兼容：版本、机型、端、环境、协议差异。
- 性能：响应时间、并发、批量、资源占用。
- 稳定性：长时间运行、重复执行、异常恢复。
- 安全：鉴权、越权、数据保护、审计。
- 体验：提示、反馈、易用性、可恢复性。
- 风险：历史缺陷、高风险组合、现场问题。

这一步产出的测试点清单，是后续用例生成的核心输入。

## 六、门禁A：确认“测什么”

门禁A用于审核需求理解、疑问闭环、功能抽取和测试点抽取。

它回答一个问题：

```text
测试对象和测试点是否已经基本清楚？
```

门禁A通过条件可以包括：

- 需求目标、范围、流程、规则和约束清楚。
- 阻塞疑问已经闭环。
- 未闭环疑问有影响说明。
- 功能清单能覆盖主要需求点。
- 测试点覆盖正向、反向、边界、状态、异常和风险。
- 测试点具备基本可测性。

门禁A未通过时，不进入正式测试设计，更不能批量生成测试用例。

如果只有部分范围通过，可以只推进已确认范围，未确认范围保留缺口和风险说明。

门禁A通过后，相关输入要标记为“已冻结”。后续如果需求、规则或范围发生变化，需要做变更影响分析。

## 七、第四步：测试点分析和维度映射

门禁A通过后，才进入测试点分析。

测试点分析要做几件事：

1. 去重：合并重复或同义测试点。
2. 拆分：把过大的测试点拆成可执行的验证点。
3. 补漏：补充遗漏的异常、边界、状态和风险点。
4. 判断可测性：确认是否有可观察证据。
5. 标记执行层级：判断适合页面、接口、数据、日志、设备或自动化验证。

然后把测试点映射到测试维度。

一种通用的八维映射方式如下：

| 维度 | 说明 |
| --- | --- |
| D1 业务场景链路 | 端到端主流程、核心用户任务、跨模块链路 |
| D2 功能规则 | 规则、状态、输入输出、分支、接口逻辑 |
| D3 性能效率 | 延迟、吞吐、并发、批量、资源消耗 |
| D4 稳定可靠 | 重复执行、异常恢复、重试、幂等、长时间运行 |
| D5 兼容适配 | 机型、版本、系统、浏览器、协议、环境 |
| D6 安全权限 | 鉴权、越权、数据保护、审计、攻击面 |
| D7 用户体验 | 提示、反馈、可理解、可恢复、操作路径 |
| D8 风险失效 | 历史缺陷、高风险失效模式、低概率高影响问题 |

维度不是越多越好。

每个需求都套满八个维度，只会制造大量低价值用例。

更合理的做法是：根据需求类型、发布风险和测试策略选择重点维度，并说明裁剪理由。

## 八、第五步：风险与优先级分析

用例设计不能只看功能点，还要看风险。

常见风险来源包括：

- 主业务链路。
- 发布门槛项。
- 历史缺陷。
- 高风险失效模式。
- 真实使用场景中的高频问题。
- 安全、权限、数据一致性问题。
- 状态流转和异常恢复问题。

风险分析要转化为优先级。

可以使用 P0 / P1 / P2：

| 优先级 | 含义 | 示例 |
| --- | --- | --- |
| P0 | 必须执行 | 核心主流程、上线准入、关键数据写入、权限边界 |
| P1 | 应该执行 | 主要异常、常见边界、重要回归、历史缺陷 |
| P2 | 视资源执行 | 低频场景、低风险组合、展示细节、辅助流程 |

对于高风险测试点，不能只停留在“已关注”。

应该明确它会通过哪条用例覆盖，或者为什么本轮裁剪、裁剪后有什么残余风险。

## 九、门禁B：确认“怎么测、测多深”

门禁B用于审核测试设计本身。

它回答的问题是：

```text
测试深度是否合理？高风险是否回补？裁剪是否有理由？
```

门禁B审核材料可以包括：

- 当前进度看板。
- 测试点分析表。
- 测试维度映射表。
- 风险回补清单。
- 追溯矩阵。
- 裁剪说明。
- 用例生成预览。

门禁B通过条件可以包括：

- 测试点无明显重复、空泛或不可测。
- 每个高优测试点有推荐测试维度。
- 主链路、历史缺陷和高风险异常已回补。
- 维度裁剪有明确理由。
- 输出范围、格式和优先级策略已确认。

门禁B通过后，才允许正式生成测试用例。

## 十、用例生成前要先做预览

正式生成大量用例前，建议先输出一份用例生成预览。

预览不是最终用例，而是让测试人员确认：

- 本轮会生成哪些模块的用例。
- 会覆盖哪些测试维度。
- 哪些内容本轮不生成。
- 哪些风险会回补。
- 哪些资料缺口仍基于假设推进。
- 输出格式是 Markdown、Excel 还是测试管理平台导入格式。

一个简单的预览结构可以是：

| 维度 | 覆盖范围 | 来源 | 备注 |
| --- | --- | --- | --- |
| D1 业务场景链路 | 核心端到端流程 | 主流程测试点 | 必测 |
| D2 功能规则 | 状态、权限、输入输出 | 功能测试点 | 必测 |
| D8 风险失效 | 历史缺陷和高风险异常 | 风险清单 | 回补 |

同时列出不生成范围：

| 内容 | 原因 | 后续处理 |
| --- | --- | --- |
| 某类低风险组合 | 本轮发布范围不涉及 | 后续回归抽样 |
| 某类专项性能场景 | 缺少压测环境 | 转专项测试 |

用户确认预览后，再生成正式用例。

如果用户只确认部分范围，就只生成已确认范围。

## 十一、正式用例的质量要求

正式测试用例不只是一个标题列表。

每条用例至少要做到可执行、可判定、可追溯。

建议字段包括：

| 字段 | 说明 |
| --- | --- |
| 用例 ID | 便于引用和追踪 |
| 所属模块 | 对应功能拆分结果 |
| 功能节点 | 对应具体功能或流程 |
| 用例标题 | 动作导向，表达验证目标 |
| 用例类型 | 主流程、异常、边界、权限、状态、数据、回归等 |
| 优先级 | P0 / P1 / P2 |
| 前置条件 | 环境、账号、数据、状态、配置 |
| 测试数据 | 明确输入或构造方式 |
| 操作步骤 | 原子化、可执行 |
| 预期结果 | 可观察、可判定 |
| 来源 | 需求、功能点、测试点、风险或历史缺陷 |
| 是否回归 | 是否进入后续回归集 |
| 是否冒烟 | 是否作为冒烟验证 |
| 自动化候选 | 是否建议自动化 |

质量自检时，可以重点看这些问题：

- 测试人员能不能按步骤执行？
- 预期结果是否明确？
- 是否存在同义重复用例？
- 高优测试点是否都有对应测试用例？
- 每条关键用例是否能追溯到需求、测试点或风险？
- 未覆盖内容是否有裁剪理由？
- 残余风险是否清楚？

## 十二、需求变更时如何处理

现实工作中，需求经常变化。

尤其是在门禁通过后，如果用户又补充新的需求说明、接口字段、状态规则、异常口径或发布范围，就不能简单继续生成用例。

测试用例设计 Skill 应该先做变更影响分析：

| 影响对象 | 是否影响 | 说明 |
| --- | --- | --- |
| 需求分析 | 是 / 否 | 是否改变目标、范围或规则 |
| 疑问清单 | 是 / 否 | 是否新增待确认问题 |
| 功能清单 | 是 / 否 | 是否新增或删除功能点 |
| 测试点清单 | 是 / 否 | 是否需要补充或删除测试点 |
| 维度映射 | 是 / 否 | 是否影响测试深度 |
| 风险优先级 | 是 / 否 | 是否改变必测项 |
| 已生成用例 | 是 / 否 | 是否需要修改、废弃或补充 |

如果影响门禁A产物，就回退到需求、疑问、功能或测试点阶段。

如果只影响门禁B产物，就回退到测试点分析、维度映射、风险优先级或输出预览阶段。

如果只是补充说明，不影响设计结果，则更新看板和说明即可。

## 十三、这套流程真正解决什么

这套工作流表面上是在规范 AI 生成测试用例。

本质上，它解决的是测试设计过程中的几个长期问题：

第一，让需求理解可见。

不是“我觉得需求是这样”，而是通过需求分析、疑问清单和门禁A把理解过程记录下来。

第二，让测试点可评审。

用例生成之前，先评审“测什么”，避免生成一堆方向错误的用例。

第三，让测试深度可解释。

通过维度映射、风险优先级和裁剪说明，解释为什么有些场景必测，有些场景抽样，有些场景本轮不测。

第四，让用例可追溯。

每条关键用例都能追溯到需求、功能、测试点或风险，后续评审、回归和资产沉淀会容易很多。

第五，让 AI 输出更稳定。

AI 不再靠一次提示词自由发挥，而是按固定流程逐步推进。

## 十四、最后总结

测试用例设计 Skill 的目标，不是让 AI 替测试人员“拍脑袋写用例”。

它更适合承担一个流程化助手的角色：

- 帮测试人员整理资料状态。
- 帮测试人员拆需求和功能。
- 帮测试人员抽测试点。
- 帮测试人员识别缺口和风险。
- 帮测试人员映射测试维度。
- 帮测试人员生成可执行、可判定、可追溯的用例。

真正重要的不是生成速度，而是生成过程是否可信。

一套好的测试用例设计 Skill，应该让 AI 在生成用例之前先学会克制：
